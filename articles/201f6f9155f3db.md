現在、AI エージェントやその他オーケストレーションを書くための言語 **Katari** を開発しています。現在 v0.1.x です。

- サイト: https://katari-lang.dev
- リポジトリ: https://github.com/katari-lang/katari

この度だいたい次のような事ができる Discord Bot をこの言語で作りました。

- 定期的なメール監視やカレンダーへの反映
- 定期的な作業、Web 監視
- 上記監視系を自発的に開始、停止する
- タスク管理、メモリー、Soul など
- その他画像編集ツールなどの利用

この記事では言語の仕様や将来の計画などを説明します！

# モチベーション

最初の動機は、オーケストレーションを抽象化することでした。OSS のオーケストレーターは YAML や Typescript のライブラリで書かれていることが多いです。

YAML で記述すると次のような問題があります。

- ファイルや module 分けが標準でない
- 変数、などの概念が標準でない
- 型付けが標準でなされない (Invalid なプログラムの記述が可能)

Typescript のライブラリでは次のような事が問題となります。

- 再起動耐性が標準でない (そのため、ライブラリでは再起動耐性が必要なところをマークなどする必要がある)
- オーケストレーショングラフが第一級ではなく、柔軟な取り扱いや Go to Definition が難しい

ここらへんを解決するために、DSL としての言語を作ろう、ということになりました。

主な特徴は以下のようなものです

- デフォルトで再起動耐性を持つ
- 構造的型付けを行う
- Parallel な Effect System を持つ (後述するが、Human-in-the-Loop の構築に使える)
- LSP, CLI, パッケージマネージャと import 文などのサポート
- MCP, Oauth の接続
- 関数を Tools として扱う

# Runtime の仕組み

Katari では、ソース (拡張子は `.ktr`) はコンパイラが中間表現に変換し、(サーバーなどに) 常駐する Runtime がそれを管理します。
アップロードのたびに Immutable な Snapshot が作られ、開発者は好きな Snapshot 内の好きな処理を動かす事ができます。

```sh
katari init my_agent && cd my_agent
katari check                 # 型検査
katari apply                 # コンパイル・バンドルして runtime に snapshot をデプロイ
katari run my_agent.main --detach
```

Katari の関数は `agent` と呼びます。次のプログラムは、毎週月曜 9:00 に処理を実行し続けるワークフローです。

```katari
@"Every Monday 09:00 JST, post the weekly digest."
agent main() -> never {
  use discord.provider(source = credentials.env(key = "DISCORD_TOKEN"))
  agent tick(time: number) {
    discord.try_send(channel = "123456789", text = build_digest())
  }
  time.watch(
    schedule = time.cron(expression = "0 9 * * 1", timezone = "Asia/Tokyo"),
    deliver_to = tick,
  )
}
```

`time.watch` は実行を始めるとキャンセルするまで実行し続け、定期的に `deliver_to` で渡された関数を実行します。この状態は永続化され、サーバーを再起動しても維持されます。 (Katari では、殆ど全ての関数が再起動耐性を持ちます。FFI などの外部への通信や副作用だけは、at-most-once で、再起動時は throw するようにしています。)

# Effect と Handler

Katari には Algebraic Effect の亜種が搭載されています。(本家 Algebraic Effects を知らなくても大丈夫です)　

まず、`request` 宣言で、中味のない関数を宣言できます。ここでは `approve` という Request を宣言してみます。
`approve` は通常の関数と同様に呼び出せますが、`approve` という関数を使った、という事を示すために、それを使った処理には `with approve` という型が付きます (省略すると推論されます)

```katari
@"Approval before an irreversible action."
request approve(description: string) -> boolean

agent deploy_if_approved() -> string with approve {
  if (approve(description = "deploy to production")) {
    run_deploy()
  } else {
    "cancelled"
  }
}
```

`approve` にどう答えるかは呼び出し側の文脈が決めます。たとえば、常に `true` を返すようにしたい場合は、以下のように記述します。`use parallel handler` が、それ以降の `approve` に意味を注入します。`handler` 内の `request` 実装では、`next` を使うことでその値を戻り値と出来ます。

```katari
agent main() -> string {
  use parallel handler {
    request approve(description : string) {
      next true
    }
  }
  deploy_if_approved()
}
```

もう少し複雑な、たとえばディスコードの UI でユーザーに質問するような Human-in-the-Loop は次のように記述できます。

```katari
agent main() -> string {
  use parallel handler {
    request approve(description : string) {
      let answer = discord.ask(
        channel = "123456789",
        prompt = f"Approve? — ${description}",
        // ボタンを二つ提示
        controls = [
          discord.button(id = "approve", label = "approve"),
          discord.button(id = "deny", label = "deny"),
        ],
      )
      // 結果によって分岐
      match (answer) {
        case discord.clicked(id => "approve", by => _) -> { next true }
        case rest -> { next false }
      }
    }
  }
  deploy_if_approved()
}
```

`deploy_if_approved` の実装を変えないまま approve の意味を切り替えることが出来るのが重要で、たとえば、この処理は常に true, この処理はユーザーへ、というのを文脈によって切り替えることが出来ます

つまり、Algebraic Effects のこの文脈依存の実装の提供、という性質を、より上位のプロセス (= agent) への ask、と捉えているのが Katari 言語の特徴です。

特に、handler が最上位までいない処理を走らせると、"Escalations" として、Runtime に溜まり、ユーザーが CLI / Admin Console から答えることが出来ます。以下は Admin ページの表示例です。

# 関数をToolsとして扱う

関数はそのまま Tool として扱え、AI に渡すことが出来ます。以下は、`search` 関数を作って AI に渡す例です。Katari では、すべての関数は型付けされ、型から直接 Input / Output の JSON Schema を導出することが出来ます。 `infer_with_tools` は内部でそれを行い、Tool Call のループを行う関数です。

`tools` 引数はただの関数列であることに注意してください。

```katari
@"Tool: search the web and return the top results as a compact digest."
agent search(@"The search query." query: string) -> string {
  tavily.digest(query = query)
}

agent answer(question: string) -> string {
  ai.infer_with_tools(
    history = [types.turn(role = "user", text = question)],
    tools = [search, web.fetch_page, e2b.run_python],
    max_steps = 8,
  )
}
```

# MCP との接続

外部の MCP サーバーのツール群は、2 通りの方法でプログラムに接続できます。

静的に使うなら `katari mcp pull` で型付きバインディングを生成出来ます。
生成後は `notion.notion_create_pages(...)` のように、サーバーのツールを型付きの関数として直接呼べます。

```sh
katari mcp pull --url https://mcp.notion.com/mcp --out src/my_agent/notion.ktr
```

`use mcp.provide` を使うことで動的に取得する事も出来ます。接続先のツール一覧を実行時に取得し、関数のレコードとして取得できます。

```katari
let tools : mcp.toolbox[mcp.scope] = use mcp.provide[mcp.scope](
  url = "https://mcp.notion.com/mcp",
  auth = mcp.oauth(name = "notion"),
)
```

# 例: Discord Bot

僕が実際に運用している Discord ボットの構成を簡略化したものがこれです。

`ai` パッケージは AI の召喚、通信周りを行うパッケージで、`ai.spawn` によって AI の召喚、 `ai.mail` によって通知を行うことが出来ます。

```katari
// AI に渡すツール
@"Tool: post a message to the home channel."
agent post_discord(@"The message text." text: string) {
  let _outcome = discord.try_send(channel = env.get_or(key = "CHANNEL", fallback = ""), text = text)
  null
}

// watcher: チャンネルの新着メッセージを AI へのメールに変える
agent channel_source(self: string) -> never {
  discord.watch_messages(
    channel = env.get_or(key = "CHANNEL", fallback = ""),
    deliver_to = agent (value: discord.message) {
      let _posted = ai.mail(to = self, source = f"discord:${value.channel}", content = value.text, hop = 0, files = value.files)
      null
    },
  )
}

// watcher: 毎朝通知する
agent morning_source(self: string) -> never {
  time.watch(
    schedule = time.cron(expression = "30 7 * * *", timezone = "Asia/Tokyo"),
    deliver_to = agent (time: number) {
      let _posted = ai.mail(to = self, source = "cron:morning", content = "朝のタスク: 今日やることを整理して報告。", hop = 0)
      null
    },
  )
}

// この AI のツール群が実行しうる request の和 (実物は使うパッケージのぶんもう少し長い)
type app_row = discord.credential | store.get | store.set | store.delete | store.list | io

agent main() -> never {
  // この記事では省略したが、Effect System と use 構文により、環境に機能を突っ込んでいく
  use discord.provider(source = credentials.env(key = "DISCORD_TOKEN"))
  use anthropic.provider(model = "claude-sonnet-5", source = credentials.env(key = "CLAUDE_API_KEY"))
  use store.workspace(path = "assistant")

  // fiber の死に対するハンドラ
  use handler {
    request region.crashed(id: string, name: string, message: string) {
      let _notice = discord.try_send(channel = env.get_or(key = "CHANNEL", fallback = ""), text = f"(${name} died: ${message})")
      next null
    }
    request region.failed(id: string, name: string, error: unknown) {
      let _notice = discord.try_send(channel = env.get_or(key = "CHANNEL", fallback = ""), text = f"(${name} failed)")
      next null
    }
  }

  // AI の召喚
  let root = use ai.route[app_row]()
  let _core = ai.spawn[app_row](
    name = "core",
    tools = [post_discord, web.fetch_page, memory.remember, memory.recall, memory.search],
    sources = [channel_source, morning_source],
    workspace = "core",
    max_steps = 16,
  )
  region.watch(nursery = root)
}
```

概ねうまく動いていて、毎日進捗報告とタスク管理をさせてるんですが、Sonnet でもだいぶ API 使用料食ってるのが現状の問題です (キャッシュは入れてるんですがね……)

# ツールチェーン

一通揃ってはいますが、改善の余地アリです。

- **CLI** : `katari init / check / apply / run / status / cancel / ...` など。npm に公開しているので、 `npm install -g @katari-lang/cli` でインストールできます。
- **LSP + VSCode 拡張** : VS Marketplace と Open VSX に出しています。
- **Runtime Image** : Runtime は Docker イメージとして配布しています。(GHCR)
- **Admin Console** : Runtime に付属する Web コンソール。Run の一覧と実行トレース、Escalation への回答、OAuth の認可、Env と Secret、Snapshot の管理、Store の中身などを UI で管理できます。
- **Package Manager** — 現状は僕が作ったライブラリだけですが、一応 registry の仕組みと Stackage みたいな Snapshot / 依存解決の仕組みは入っています

# 将来について

Katari の v0.1 としてやりたいことはある程度できてると思うんですが、v0.2 では、大幅に言語機能を変える予定です。まず、次の観察ができます

- AI Agent の組織を考えると、上下関係と、並列で動く Agent がありそう。(木構造)
- 木構造の節で何かしら Context を与えてあげて、これより下ではこの機能が使えます、という事を制御したい

Katari でまだできていない事として

- 常駐する木構造に対して更新パッチを当てたい
- 上からの状態を伝播したい

これらを総合すると、かなり UI (DOM 構造) に近いことが分かります。つまり、インターネット上に常駐する "Agent Tree" に対して、Hydration により差分を適用、`useState / createState` による状態管理、などが考えられます。

v0.2 では、より Component Based な言語にして、一段階抽象化された言語機能を提供したいと思っています。

(あと、Documents とかが大体 Fable 君のお手製なので、そこの校正がしばらくのタスクです)

# まとめ

- Katari はオーケストレーションのためのDSLで、Effect System、Parallel 実行、再起動耐性などが標準に入っています。
- 関数は型からスキーマが導出され、そのまま AI のツールになります
- MCP との接続が標準装備
- 複数 AI の協調などは `ai.mail` と `ai.spawn` で行えます (ここらへんの API はまた変わるかも……)
- v0.2 では Component based になります

v1.0 までは全然 API を固定する気が無いので、今は遊びで使ってみてください！ バグがあったら Issue など立ててくれると嬉しいです。
